# Decisions

Format: **decision**: rationale. `[given]` = set by the project owner. `[confirmed]` = proposed during planning, confirmed by the owner on 2026-11-12. Append new decisions at the end of the relevant section with the phase that introduced them.

## Product scope

- **[given] Users are technical product people. This is the owner's own tool and a portfolio piece**: optimize for clarity and demo quality, not multi-tenant scale.
- **[given] Software projects only**: the spec template and ticket rules assume software.
- **[given] No "does this already exist?" check**: out of scope; the user brings the idea.
- **[given] Out of scope for V0: running Claude on tickets, GitHub Actions, custom kanban, starter templates, per-ticket model routing, user-supplied API keys**: keep V0 small. Seams: model config is per task, the ticket schema has room for metadata, and the GitHub layer is a module of its own.
- **[confirmed] Sign-in restricted to an allowlist of GitHub logins (`ALLOWED_GITHUB_LOGINS` env)**: the server spends the owner's Anthropic key, so a public deploy must not let strangers run up the bill. Non-allowlisted users see a friendly "private preview" page.

## Stack

- **[confirmed] Next.js App Router + TypeScript strict**: one deployable unit for UI and server routes, first-class streaming route handlers, and easy Vercel deploys.
- **[confirmed] Vercel for deployment**: zero-config for Next.js; streaming route handlers with a raised `maxDuration` cover long Opus calls.
- **[confirmed] pnpm, Node 24 LTS**: fast installs, strict dependency resolution, current LTS.
- **[confirmed] Tailwind for styling**: fast to build a clean UI without a component-library dependency.
- **[confirmed] Zod v4 for all schemas**: works with the Anthropic SDK's `zodOutputFormat` helper, so one schema drives LLM output, validation and TS types.
- **[confirmed] `arctic` (GitHub OAuth client) + `iron-session` (encrypted, signed cookie) instead of Auth.js**: Auth.js moved to security-patch-only maintenance after joining Better Auth (Sept 2025), and v5 never left beta. Better Auth's stateless (no-DB) mode is newer and less proven. We need only one provider, no DB and full control over where the token lives, and two small maintained libraries do exactly that.
- **[confirmed] Octokit (`@octokit/rest` + `@octokit/plugin-retry` + `@octokit/plugin-throttling`)**: the official client, typed, with built-in retry and secondary-rate-limit handling, which matters when creating many issues in a burst.
- **[confirmed] `@xyflow/react` (React Flow) + `@dagrejs/dagre` for the graph**: React Flow handles rendering, pan and zoom; dagre gives a deterministic top-to-bottom DAG layout. Both are maintained and standard for this job.
- **[Phase 0] Node 26 LTS instead of Node 24 (supersedes the Node part of "pnpm, Node 24 LTS")**: Node 26 became Active LTS in Oct 2026 and is what the dev machine runs. Enforced with `engines` (`>=26 <27`), `engine-strict` and `.nvmrc`.
- **[Phase 0] TypeScript 6.0.3, not 7.x**: `typescript-eslint` 8.72 supports only `typescript <6.1.0`. Revisit when it supports TS 7.
- **[Phase 0] Exact version pins (`save-exact=true` in `.npmrc`)**: reproducible installs. Dependencies used only in later phases (`@xyflow/react`, `@dagrejs/dagre`, Playwright) are checked and pinned in the phase that first uses them, not up front.
- **[Phase 0] `@octokit/oauth-methods` replaces `arctic` for the GitHub OAuth flow (supersedes the `arctic` half of the decision above; `iron-session` stays)**: every `arctic` version now carries npm's generic "Package no longer supported. Contact Support" notice (typical of a registry takedown), and its last release was 3.7.0 in May 2025. `@octokit/oauth-methods` is GitHub's official Octokit package, shares Octokit's request layer (so MSW mocking works the same way), and provides `getWebFlowAuthorizationUrl()` and `exchangeWebFlowCode()`. We still own the security-sensitive parts: always pass our own crypto-random `state` (the library defaults to `Math.random()`), store it in the cookie and check it on the callback. Alternatives considered: writing the flow ourselves (no dependency, but we'd own GitHub's quirks, such as token-endpoint errors returned with HTTP 200) and `oauth4webapi` (generic OAuth 2 with PKCE helpers; the fallback if PKCE turns out awkward). Phase 3 starts by checking whether GitHub supports PKCE for OAuth Apps; if it does, we add the PKCE parameters ourselves, since `@octokit/oauth-methods` doesn't document them.

## LLM

- **[given] Sonnet for the interview, Opus for ticket breakdown, model IDs in config**: interview turns must feel fast, and breakdown needs the strongest reasoning.
- **[confirmed] Model IDs: interview `claude-sonnet-5-5`, ticket generation and edit-impact proposals `claude-opus-5-5`**: the current Sonnet and Opus, checked against current Anthropic docs (Nov 2026). Use the exact IDs with no date suffix. They live in `src/lib/llm/config.ts`, keyed by task (`interview`, `ticketGeneration`, `ticketRevision`), which is the seam for later per-ticket routing.
- **[confirmed] Edit-impact proposals use Opus**: reasoning about dependency changes is the same kind of work as the breakdown. It's a config value, so it's cheap to switch to Sonnet if latency bothers us.
- **[confirmed] Official `@anthropic-ai/sdk`, no wrappers (no Vercel AI SDK, no LangChain)**: fewer layers, direct access to structured outputs, streaming and typed errors.
- **[given] The LLM fills the spec through tool use/structured output, never parsed free text.**
- **[confirmed] Interview mechanism: streamed text reply plus an `update_spec` tool (`strict: true`) carrying a partial spec patch, plus a `finish_interview` tool**: the user sees the question stream in while the spec fills in alongside. Forced `tool_choice` (`any`/`tool`) returns a 400 on Sonnet 5.5 and Opus 5.5, so we use `tool_choice: auto`, instruct via the system prompt, and validate every tool input with Zod server-side.
- **[confirmed] "LLM decides when complete" is enforced by the app too**: `finish_interview` is accepted only if `isSpecComplete(spec)` holds (all required fields filled, `openQuestions` empty, every feature has ≥1 acceptance check). Otherwise the server returns an error `tool_result` naming the gaps and the interview continues. The LLM decides, but the invariant is never broken.
- **[confirmed] Ticket generation uses structured outputs (`client.messages.parse` / `output_config.format` + `zodOutputFormat`) on a streamed request**: we get schema-valid JSON for the whole ticket list with no tool loop. Streaming plus `finalMessage()` avoids HTTP timeouts on long Opus outputs. After parsing, the output also goes through DAG validation, and one automatic repair retry includes the validation errors.
- **[confirmed] Thinking: adaptive (the default). Effort: interview `low`, ticket generation `high`, revisions `medium`, all in config**: on these models effort is the only thinking control (disabling thinking returns a 400 on Opus 5.5). Chat should be snappy, and breakdown quality matters most.
- **[confirmed] Interview conversation is append-only**: current models bind thinking blocks to an unedited history. Edits the user makes to the spec mid-interview are sent as a new message describing the change, never by rewriting earlier turns.
- **[confirmed] Prompt caching on the system prompt and conversation prefix**: each interview turn resends the full history, and caching cuts cost and latency.
- **[confirmed] Handle `stop_reason: "refusal"` and `max_tokens` explicitly, and enable the server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`)**: recommended default for these models. A false-positive refusal on a benign spec reroutes instead of failing.
- **[given] V0 uses the owner's Anthropic key from env (`ANTHROPIC_API_KEY`)**: user keys are out of scope. The client is built in one factory, the seam for adding per-user keys later.
- **[Phase 4] `update_spec` is not strict; `finish_interview` is (amends the "`update_spec` (`strict: true`)" part of the interview mechanism decision)**: in a live check the API rejected the strict `update_spec` with "The compiled grammar is too large". It's a union of 21 op variants, several with nested unions. Of the options (splitting it into smaller strict tools, which might still exceed the total grammar size, or loosening its schema until strict guarantees almost nothing), the owner chose to drop strict on that one tool. Nothing is lost on validation: `applySpecPatch` already checks every input, and an invalid one comes back as an error `tool_result` the model corrects. `update_spec` gets the plain `z.toJSONSchema` output, so the model sees the real length, pattern and size limits. Strict tools go through the SDK's `transformJSONSchema` (`@anthropic-ai/sdk/lib/transform-json-schema`), which turns `oneOf` into `anyOf`, moves unsupported limits into descriptions and closes every object (`betaZodTool` doesn't run it). `update_spec` takes `{ ops }`, since tool inputs must be objects. A snapshot test keeps the tool JSON byte-stable for caching.
- **[Phase 4] The current draft is never put into the prompt**: the model sees the spec through its own `update_spec` calls in the history, and every `update_spec` result lists what is still missing. The history stays append-only and the cached prefix stays stable. User edits arrive as messages (Phase 6).
- **[Phase 4] One interview request runs at most 5 model calls (`INTERVIEW_MAX_STEPS`), then returns `loop_limit`**: a guard against a model that keeps calling tools. Within one response, `update_spec` calls run before `finish_interview`, so a finish is judged against the updates made alongside it. Results keep the calls' order.
- **[Phase 4] After `finish_interview` is accepted, no further model call is made**: the server sends `complete`, and the history ends with that `tool_result`. The next user message (for example from "Back to interview") is appended after it.
- **[Phase 4] `eager_input_streaming` stays off for the interview tools**: spec patches are small, and with it on, the API no longer checks tool inputs against the strict schema.
- **[Phase 4] Mid-output refusal fallbacks are echoed by the API's rules**: before the last `fallback` block, only text blocks are stored and sent back. Tool calls from the declined attempt are never run. Refusal, `max_tokens` and `model_context_window_exceeded` are checked before any tool in the response runs.
- **[Phase 4] The Anthropic client keeps the SDK's default retries (2, for 429, 5xx and connection errors)**: one interview turn is short, so a quick automatic retry beats showing an error. Errors that remain are mapped by class (and by the SSE `error` event's type mid-stream) to `rate_limited`, `overloaded`, `connection`, `bad_request`, `server_config`, `refusal`, `max_tokens`, `loop_limit` or `unknown`, and logged with the request id.
- **[Phase 5] Billing failures get their own `billing` code, not reworded `bad_request` copy**: an exhausted credit balance arrived as a 400 `invalid_request_error`, and the `bad_request` copy ("start over") sends the user the wrong way. `codeForError` checks first for `billing_error` or a "credit balance is too low" message, whatever the status, and the copy says the owner needs to top up. Not retryable. Rewording `bad_request` to cover both was considered, but it would make the common case vaguer.

## Spec

- **[given] Fixed template as a Zod schema**: problem/goal, target user, core features (each with plain-English acceptance checks), out of scope, project type, data model (entities + relationships), integrations/external APIs, auth needs, deployment target, constraints/preferences, open questions.
- **[confirmed] Lists are arrays of objects with stable `id`s (features, entities, relationships, integrations, open questions)**: patches and UI edits target items by id, so reordering and editing never mismatch.
- **[confirmed] "None" is an explicit value for optional-in-practice fields (integrations, auth needs)**: an empty array is ambiguous (not asked yet, or not needed?). Completeness requires either items or an explicit `none: true` with a reason.
- **[confirmed] SPEC.md is rendered deterministically from the schema (pure function, snapshot-tested), not written by the LLM**: what the user approved is exactly what gets committed.
- **[confirmed] Spec editing is a structured form per field, not a raw Markdown editor**: keeps the spec schema-valid at all times.
- **[confirmed] Editing the spec after tickets exist marks the tickets stale and offers regeneration (no silent changes)**: keeps spec and tickets consistent without surprising the user.
- **[Phase 1] Spec fields beyond the template: `name` (SPEC.md title, later the suggested repo name), and problem/goal split into `problem` and `goal`. `projectType` is an enum (`web-app`, `mobile-app`, `cli`, `library`, `api-service`, `desktop-app`, `other`) plus free-text `detail`**: an enum renders and prompts consistently, and `other` + detail covers the rest.
- **[Phase 1] `dataModel` also takes an explicit `none` with a reason (extends the integrations/auth rule)**: stateless tools such as CLIs and libraries would otherwise need made-up entities to count as complete.
- **[Phase 1] Ids are assigned by the caller with a fixed prefix per list (`F` features, `E` entities, `R` relationships, `I` integrations, `Q` open questions), using `nextId` (highest + 1)**: the LLM and the UI pick ids directly, with no round-trip, and ids stay readable in prompts. Wrong prefixes and duplicates are rejected by the schema.
- **[Phase 1] Acceptance checks are plain strings, replaced as a whole when their feature is upserted**: per-check ids add nothing, since the form edits checks by position.
- **[Phase 1] Patches are ordered `set` / `upsert` / `remove` ops applied all-or-nothing, and the result is re-validated as a whole**: one bad op leaves the draft unchanged, and cross-item rules (unique ids, relationships pointing at known entities) hold after every patch. Lists with ids change only through upsert and remove. Upserting into a `none` data model or integrations section turns it into a list.
- **[Phase 1] `SpecSchema` (complete spec) enforces the completeness rules and is branded**: renderers and the creation route can only receive a spec that passed the check. `outOfScope` and `constraints` may be empty.
- **[Phase 1] SPEC.md starts with `<!-- keel:spec v1 -->` and leaves out open questions**: Phase 10 uses the marker to recognise a Keel repo it can resume into, and the version allows format changes later. A complete spec has no open questions, so the section would always read "None".
- **[Phase 1] The transcript is `{ role: "user" | "assistant", text }[]`, visible text only**: Phase 4 maps its full history (including tool blocks) to this shape before rendering `docs/interview.md`.

## Tickets

- **[given] One user-visible behavior per ticket, ~3–8 files, targeting a 200–500 line diff. Fields: title, description, acceptance checks, S/M/L, dependencies.**
- **[confirmed] Tickets use stable local ids (`T1`, `T2`, …) before creation**: dependencies reference local ids, which map to issue numbers only at creation time.
- **[given] Dependencies must be a valid DAG, validated after generation and after every edit**: checks for cycles, unknown ids and self-references. Errors name the offending tickets and the cycle path.
- **[given] After a user edit, the LLM proposes updates and the user approves them. Nothing changes silently.**
- **[confirmed] Proposals are a typed list of operations (`updateTicket`, `addDependency`, `removeDependency`, `addTicket`, `deleteTicket`), each with a reason, accepted or rejected individually**: easy to review and test. Any combination of accepted ops is re-validated as a DAG before it's applied, and invalid combinations are blocked with an explanation.
- **[confirmed] Proposals are requested on demand ("Check impact") after a batch of edits, not on every keystroke**: avoids an Opus call per character and lets the user make several edits first. Creation is blocked while edits are unchecked, so impact review can't be skipped by accident.
- **[confirmed] Deleting a ticket that others depend on is allowed but leaves the DAG invalid until it's resolved**: the validation UI and impact proposals guide the fix. Creation is blocked while the DAG is invalid.
- **[Phase 2] Ticket fields are exactly `id`, `title`, `description`, `acceptanceChecks` (1–20, each ≤500 characters), `size` (`S|M|L`) and `dependsOn` (unique ids, ≤20), with at most 100 tickets. No `featureIds` or metadata bag yet**: at least one check mirrors the spec's feature rule. The 500-character cap on each check keeps the worst-case issue body far below GitHub's 65,536-character limit. Extra fields can be added when something needs them.
- **[Phase 2] `TicketListSchema` checks shape and unique ids only. The DAG is checked separately by `validateDag`**: a user edit may leave the graph invalid (see the delete rule above), so an invalid graph must still be representable and reportable.
- **[Phase 2] `validateDag` returns typed errors (`unknownDependency`, `selfDependency`, `cycle` with its path)**: reference errors come first, in ticket order. Then there's one shortest cycle per strongly connected group, starting at its lowest id. A self-reference is reported once, not also as a cycle. The traversal is iterative (Tarjan), so large inputs can't overflow the stack. `formatDagError` gives the one-line text used by the UI, the repair prompt and proposal validation.
- **[Phase 2] `topoSort` breaks ties by input position**: the output is deterministic, and an already-ordered list (such as the LLM's output) comes back unchanged, so the order users see matches what they reviewed.
- **[Phase 2] Proposal op shapes**: `updateTicket { id, changes }` changes only title, description, acceptance checks or size. Dependencies change only through `addDependency` / `removeDependency { ticket, dependsOn }`. Then `addTicket { ticket }` and `deleteTicket { id }`. Every op has a `reason`. `deleteTicket` doesn't remove edges into the deleted ticket, so deleting one that's still needed is blocked by validation rather than silently rewiring. Redundant ops (adding an existing dependency, removing a missing one) are errors. The UI accepts ops by their position in the proposal, so ops have no ids. `applyProposalOps` is all-or-nothing, like `applySpecPatch`.
- **[Phase 2] Issue body format v1 (refines the format decision above)**: `<!-- keel:ticket=Tn v1 -->`, then the description, `## Acceptance checks` with `- [ ]` items, and `## Dependencies` with one `Depends on #N` line each (or `None.`). The marker gained a version, like `keel:spec v1`, so the format can change later. The parser also accepts the unversioned form and rejects other versions. Size is kept only on the `size:*` label, so relabelling on GitHub is the single source of truth.
- **[Phase 2] `parseIssueBody` is lenient, because GitHub is the source of truth after creation**: it accepts ticked boxes, CRLF, missing sections and text added above the marker. Sections are found from the last `## Dependencies` heading and the last `## Acceptance checks` heading before it, so a description containing those headings or `Depends on #N` doesn't produce phantom dependencies.
- **[Phase 2] Shared schema helpers (`boundedText`, `prefixedId`, `reportDuplicates`) and the prefix-generic `nextPrefixedId` live in `src/lib/validation.ts` and `src/lib/ids.ts`**: spec and ticket schemas use the same text, id and uniqueness rules and the same error messages.

## GitHub

- **[given] GitHub OAuth, minimum scopes. The token stays server-side in an encrypted session, never sent to the client.**
- **[confirmed] Use an OAuth App (not a GitHub App)**: a GitHub App's user token can create a repo, but the app then has to be installed on it to write issues, which adds friction for no V0 benefit.
- **[confirmed] Scope: `public_repo` only. Keel creates public repos**: `public_repo` is the minimum that allows creating a repo, committing files, and creating labels and issues. Private repos need `repo`, which grants read/write to all of the user's private code, a big ask for a portfolio tool. If you want private repos, we switch to `repo`, a one-line change plus re-consent.
- **[confirmed] No GitHub Project board in V0, just link to the issues list**: Projects v2 needs the extra `project` scope and a GraphQL integration, and our own graph view already covers visualization. A board fits naturally alongside the later kanban work.
- **[given] Repo is created in the user's own account (`POST /user/repos`).**
- **[confirmed] Initial commit via the Git Data API (tree + commit + ref update) containing `SPEC.md`, `docs/interview.md` and a minimal `README.md`**: one clean commit instead of three contents-API commits. The repo is created with `auto_init: true` so a base ref exists.
- **[given] Issues are created in topological order, so bodies contain real `Depends on #X` lines. Labels: `size:S|M|L`, `status:backlog`.**
- **[confirmed] Issue body format is fixed and machine-parseable**: description, `## Acceptance checks` checklist, one `Depends on #N` line per dependency, and a hidden marker `<!-- keel:ticket=T3 -->`. Rendering and parsing are pure functions, round-trip tested. Changing it later breaks parsing of existing repos.
- **[confirmed] Labels are created idempotently before issues (create, treat 422 "already exists" as success)**.
- **[confirmed] Creation is resumable and idempotent, with no DB**: the client keeps a creation log in localStorage (repo full name, ticket id → issue number). A server "reconcile" step lists the repo's issues and maps existing ones by their `keel:ticket` marker, so a retry skips what already exists and continues in topological order. The UI shows per-step status (repo, commit, labels, each issue) and a "Resume" button on failure.
- **[confirmed] Repo name collision is caught before creation**: we check name availability up front and suggest an alternative. If the repo exists and contains a Keel SPEC.md marker, we offer to resume into it; otherwise we refuse.
- **[confirmed] Issue creation runs sequentially with Octokit throttling and retry**: topological order needs earlier issue numbers, and sequential writes stay under GitHub's secondary rate limits.
- **[given] Dependency graph is read-only, built from the created issues by parsing `Depends on #X`.**
- **[confirmed] Graph loads the repo's issues labelled `status:backlog` plus any carrying the Keel marker, and can be reopened later from a repo URL**: GitHub is the source of truth, so the graph reflects later edits made on GitHub.
- **[Phase 3] PKCE (`S256`) on top of `state`**: GitHub has supported PKCE for OAuth Apps since July 2025, and only accepts `S256`. `@octokit/oauth-methods` has no PKCE options, so we append `code_challenge` to the URL it builds and pass `code_verifier` through `request.defaults()`. That keeps the library's handling of GitHub's "error with HTTP 200" responses. The `state` and verifier live in a sealed `keel_oauth` cookie that expires after 10 minutes, is cleared on every callback and is compared in constant time.
- **[Phase 3] Session: a sealed `keel_session` cookie (`iron-session`) holding only `{ token, login, avatarUrl }`, valid for 7 days**: GitHub OAuth App tokens don't expire, so the cookie lifetime sets how often users sign in again. The GitHub user id gets added only when something needs it. Cookies are httpOnly, `SameSite=Lax` and `Secure` except for plain-HTTP outside production. Cookie contents are Zod-validated on read, and a tampered or unreadable cookie counts as signed out (logged as a warning).
- **[Phase 3] The token stays inside `src/lib/auth`**: UI code gets `SessionUser` (the session without the token) from `getSessionUser()` / `requireUser()`. `getSession()`, which includes the token, is for server code that calls GitHub. The header and user menu are server components, so no client component touches the session.
- **[Phase 3] Login and avatar come from `GET /user` after the token exchange, which returns neither**: the avatar URL must be `https://avatars.githubusercontent.com`, the only host allowed in `images.remotePatterns`. The exchange fails if the granted scopes lack `public_repo`.
- **[Phase 3] Rejected users' grants are deleted (`DELETE /applications/{client_id}/grant`)**: this applies both to users not on the allowlist and to users whose `GET /user` call fails. Deleting the grant takes Keel off their Authorized OAuth Apps list rather than leaving an authorization we'll never use. A failed deletion is logged and doesn't change what the user sees.
- **[Phase 3] `getSession()` calls `await connection()` before reading the cookie**: unsealing checks expiry with `Date.now()`, and with Partial Prefetching Next prerenders cookie reads, then rejects time-dependent values during the prerender. The error shows only in a dev render with a real cookie, not in tests or `next build`. Session-dependent UI therefore renders at request time and isn't prefetched.
- **[Phase 3] Sign-out is `POST /api/auth/logout` only, answered with a 303**: a GET would let any link or image on another site sign the user out.
- **[Phase 3] Route protection: `proxy.ts` checks for the session cookie on `/app/:path*`, and every protected page calls `requireUser()`**: Next 16's docs limit Proxy to quick cookie checks, and layouts don't re-run on client navigation. Callback failures redirect to `/?error=signin` or `/?error=cancelled` with friendly copy. Users not on the allowlist go to `/private-preview`.
- **[Phase 3] Server logs are JSON lines from `src/lib/log.ts`, and errors are reduced to name, message and status**: Octokit errors carry their request, whose body can hold the client secret or a token, so a raw error is never logged.

## State & persistence

- **[given] No database. Interview state is client-side until the repo is created.**
- **[confirmed] Client state is one versioned, Zod-validated object in localStorage (`keel:project:v1`), managed by a small reducer**: it survives a refresh, and the version field allows migrations. A corrupt or old state is reported, never silently dropped (export JSON first, then reset).
- **[confirmed] One project in progress at a time in V0**: keeps the state shape and UI simple. The state object is keyed so multiple projects can be added later.
- **[confirmed] The server is stateless: each request carries what it needs (history, spec, tickets), and every body is Zod-validated with size limits**: no DB, and the client is never trusted.
- **[Phase 4] The client stores the raw interview history (Anthropic message params), not only visible text**: append-only history with thinking blocks requires thinking blocks (with signatures), tool calls and tool results to be sent back unchanged. `HistorySchema` accepts only the block types the interview produces, each with size limits, and the request body is capped at 2 MB. `toTranscript` derives the visible text for `docs/interview.md`.
- **[Phase 5] `keel:project:v1` shape: `{ version: 1, currentProjectId, projects: { [uuid]: { id, createdAt, updatedAt, stage, history, draft, spec } } }`, with `stage` `interview | review` for now**: confirmed by the owner. `history` holds committed turns only, and `spec` is set by `complete`. Projects are keyed by id so several can be added later, but starting a new one replaces the stored one in V0. Later phases add stages and fields, and a breaking change means a `v2` key plus a migration.
- **[Phase 5] Streamed text and `specPatch` drafts are provisional in the client too**: the reducer keeps them in a transient slice that is never saved, commits the draft together with the `turn` that carries it, and drops both on `error`. The user's message is stored before the request, so "Try again", and the "didn't get a reply" prompt after a refresh, resend the stored history unchanged.
- **[Phase 5] Unreadable saved state is offered as a download of the raw text, untouched, before reset**: Reset asks for confirmation unless the user downloaded first, and it overwrites the key with an empty state. A full or blocked localStorage shows a warning banner, and the interview keeps running in memory.
- **[Phase 5] The workspace renders client-only (`next/dynamic`, `ssr: false`)**: localStorage doesn't exist on the server. State loads in a lazy `useState` initializer and saves when an action is applied (persisted changes only, so text deltas don't write). React's lint rule forbids `setState` in effects, which rules out the load-in-effect pattern.
- **[Phase 5] Known limit: after a non-retryable refusal, the next message is appended after the refused one, not substituted for it**: trimming the history would be allowed (no assistant content follows that message), but refusals on spec content are rare and the server-side fallback is on. Revisit if refusals show up in practice.

## Streaming & errors

- **[confirmed] Stream interview replies (text deltas + spec-patch events) over a route handler using SSE-formatted `ReadableStream`**: perceived speed matters most in chat. Spec updates show up live.
- **[confirmed] Ticket generation streams progress events (started, thinking, N tickets parsed, validated) rather than token text**: the user sees progress during a long Opus call without reading raw JSON.
- **[confirmed] Errors are a typed union per module, mapped to friendly UI copy, with details in server logs (request ids included)**: follows the error-handling rule. Anthropic errors are caught most-specific-first (rate limit, overloaded, bad request, connection). Retryable ones get a "Try again" action.
- **[Phase 4] Interview SSE events: `text`, `specPatch { ops, draft }`, `turn { messages }`, `complete { spec }`, `error { code, message, retryable }`, validated by `InterviewEventSchema`**: `turn` (added in Phase 4) commits one model response plus its tool results to the stored history. `text` deltas before it are provisional, and on `error` the client drops them, so a retry always resends a consistent history. `specPatch` carries the server's resulting draft, which the client stores instead of applying the ops again itself.
- **[Phase 4] `POST /api/interview` re-checks the allowlist on every request, not just at sign-in**: the route spends the owner's API key, and the list may have changed since the session was created.
- **[Phase 5] `eventsource-parser` (4.1.3, `EventSourceParserStream`) parses the interview SSE stream in the browser**: confirmed by the owner over a hand-written parser. `sendTurn` validates every event with `InterviewEventSchema`, caps buffering at the request size limit, and turns HTTP errors (401 → sign in again, 400, 413), malformed events and a stream that ends before a `turn` or `complete` into one typed client error.
- **[Phase 5] The interview tool names live in `tool-names.ts`**: `HistorySchema` needs them and runs in the browser. Importing them from `tools.ts` would pull the SDK's schema transform into the client bundle.

## Testing & tooling

- **[confirmed] Vitest + Testing Library for unit and component tests**: fast and ESM-native, and works with Next.
- **[confirmed] MSW mocks GitHub and Anthropic at the HTTP layer**: both SDKs use `fetch`, so tests exercise our real SDK calls against recorded-shape fixtures. Anthropic streaming is mocked with SSE fixtures.

- **[confirmed] ESLint (flat config, `eslint-config-next`, `typescript-eslint` strict) + Prettier; `pnpm check` = lint + typecheck + test**: one command gates every commit.
